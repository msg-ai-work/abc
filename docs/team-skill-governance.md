# 팀 Skill 운영 모델

## 목적

AI Harness는 팀장이 공통 실행 구조와 가드레일을 관리하고, 엔진·기술지원(발송클라이언트)·웹 담당 팀원은 각 업무 지식을 Skill로 작성·개선하는 방식으로 운영한다.

## 역할 분담

| 구분 | 팀장 | 업무 담당 팀원 |
|---|---|---|
| Harness 구조 | 설계·변경 승인 | 의견 제시 |
| Agent/Workflow | 공통 표준 관리 | 업무 적용 피드백 |
| Rule/Guardrail | 최종 승인 | 업무 규칙 제안 |
| Domain Skill | 구조/품질 기준 승인 | 작성·개선 Owner |
| PR Review | Harness/공통 변경 필수 승인 | 자신의 Domain Skill 1차 검토 |
| Production 결정 | 사람 승인 원칙 유지 | 검증 증적 제공 |

## Domain Skill 영역

- `engine`: SMS/MMS/RCS GW 엔진, 큐/브로커, 발송 처리, 재처리, 장애 분석, 성능/안정성
- `tech-support-client`: 고객사 발송클라이언트 설치·설정·연계·로그수집·장애진단·호환성
- `web`: 고객/관리자 웹, API 연계, 인증/권한, FE/BE 변경, 운영 점검

## 변경 절차

1. 담당자가 `skill/<domain>/<topic>` 브랜치를 생성한다.
2. 자신의 Domain Skill을 수정하고 실제 업무 사례/체크리스트를 반영한다.
3. 최소 1개의 재현 가능한 예시 또는 점검 항목을 추가한다.
4. PR을 생성하고 변경 이유, 적용 범위, 검증 방법을 기록한다.
5. 공통 Harness에 영향을 주면 팀장 승인을 필수로 한다.
6. Merge 후 Git main을 SSOT로 사용한다.

## Skill 작성 원칙

- 사람이 실제로 반복 수행하는 판단 절차를 적는다.
- 단순 설명서가 아니라 AI가 순서대로 실행할 수 있는 체크리스트로 작성한다.
- 입력, 판단 기준, 실행 절차, 산출물, 금지사항을 명확히 구분한다.
- 운영 명령은 Production 자동 실행을 금지하고 사람 승인 Gate를 둔다.
- 개인정보, 인증정보, 고객 원문 데이터는 Skill/예시에 저장하지 않는다.
- 장애 사례에서 얻은 교훈은 재사용 가능한 규칙으로 일반화한다.

## 운영 : 개발 = 6 : 4 반영

미디어로그 업무 특성상 Skill backlog도 운영 60%, 개발 40%를 기본 가이드로 잡는다. 운영 Skill은 장애 진단, 반복 점검, 고객 기술지원, 배포 전후 검증을 우선 자동화하고, 개발 Skill은 영향분석, 구현, 테스트, PR Review 품질 향상에 집중한다.

## 권장 KPI

- 운영: MTTR, 반복 문의 처리시간, 수동 점검시간, 장애 재발률
- 개발: 요구사항→PR Lead Time, 리뷰시간, 재작업률, 결함 유출률
- Skill: 월간 사용 횟수, 재사용률, 실패/수정 횟수, 최신화 경과일
